# ネットワーク公開範囲の見直しとIPv6確認

## 位置づけ

これは2026年10月3日時点の構成で行った見直しの記録です。当時はUbuntu Serverを中心にサービスを運用しており、現在の2ノードProxmoxクラスタ構成とは異なります。公開範囲を小さくする手順と、IPv4とIPv6を分けて確認する考え方を残すための事例です。

## 変更前の問題

変更前は、ルーターのDMZ機能で外部からの通信をUbuntuサーバーへ広く転送し、不要な着信はサーバー側のホストファイアウォールで遮断していました。

動作はしていましたが、次の問題がありました。

- 境界にあるルーターで破棄できる外部スキャンまでサーバーへ到達する
- サーバー側の遮断ログが大量に残り、本当に必要な通信が埋もれやすい
- ルーター、ホストファイアウォール、サービスの待受の関係を一目で説明できない
- IPv4側だけを確認すると、IPv6側の公開状態を見落とす可能性がある

## 見直しの方針

特定の機能を有効・無効にする前に、実際に必要な通信を先に特定しました。そのうえで、次の3層を照合しました。

1. ルーターが外部から転送する通信
2. ホストファイアウォールの許可・遮断
3. サービスが実際に待ち受けている通信

## 行った作業

### 1. 現在の状態を棚卸しする

変更前に、サービスの待受、ホストファイアウォール、ルーター設定、ログを確認しました。設定変更前の状態と設定バックアップを保存し、問題があれば戻せる状態にしてから作業しました。

### 2. DMZから必要最小限の転送へ移行する

必要な通信だけを個別に転送する設定を先に作り、外部から必要な接続ができることを確認しました。その後にDMZを解除し、待受、ファイアウォール、ログを再確認しました。

代替経路を確認する前にDMZだけを止めなかったことで、必要なサービスを止めずに公開範囲を縮小できました。

### 3. 来訪者用ネットワークを分離する

来訪者用Wi-Fiを通常のLANから分離し、来訪者側から通常LANへ到達しないことを実通信で確認しました。あわせて、WPSやAOSS、使っていない共有機能なども整理しました。

UPnPは全面的には無効化せず、ゲーム機用途に限定しました。サーバーの公開はUPnPへ任せず、手動設定で責任範囲を分けた点が重要です。

### 4. ルーターのsyslogを集約する

ルーターのログを、LAN内限定でログ収集側へ送る構成にしました。受信側の待受と送信元を絞り、ログが実際に届くことと、保管・ローテーションが機能することを確認しました。

これにより、ネットワーク機器側の変化もサーバーのログとあわせて追えるようになりました。

### 5. IPv6を別枠で確認する

IPv6については、IPv4の設定から類推せず、次の項目を個別に確認しました。

- グローバルIPv6アドレスが付与されているか
- デフォルトルートが存在するか
- 外向きのIPv6通信が成功するか
- サービスがIPv6でも待ち受けているか
- ホストファイアウォールにIPv6側の許可があるか
- ルーターが外部からの新規接続を遮断しているか
- 意図しないブリッジ設定が有効になっていないか

今回はIPv6ブリッジは使わず、ルーターで制御する構成を選びました。

## 結果

- 外部からサーバーへ到達する通信を、必要なものだけへ絞れた
- ルーターとホスト側の両方で、公開範囲を説明できる構成になった
- 来訪者用ネットワークを通常LANから分離できた
- ルーターのログを継続的に集約できるようになった
- IPv6をIPv4とは別に確認する手順を残せた

## 学んだこと

- ホストファイアウォールで遮断できていても、境界で不要な通信を受け取らない構成の方が運用しやすい
- 公開を止める作業では、代替の転送設定を作り、接続確認をしてから旧設定を外す順序が重要になる
- IPv4の到達性だけでは公開状態を判断できない。IPv6のアドレス、経路、待受、ファイアウォールは別々に確認する必要がある
- 「設定した」項目と「実通信で確認した」項目を分けて記録すると、後から状態を判断しやすい
