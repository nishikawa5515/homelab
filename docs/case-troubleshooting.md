# メモリ障害と10GbE経路の切り分け

障害対応で重視したのは、最初の推測を早く確定させず、条件をそろえた試験と比較で原因を狭めることです。ここでは、メモリ障害とネットワーク経路という異なる2件の切り分けをまとめます。

## 事例1：メモリエラーをDIMM単体試験で切り分ける

### 状況

Ubuntuサーバーでメモリエラーが発生しました。BIOS更新直後はエラーが再現しなかったため、一度はファームウェア側の問題が改善したように見えました。しかし追加試験で再発し、ハードウェア側を含めた再調査が必要になりました。

### 行った切り分け

- メモリテストを長時間実行し、エラーが実際に再現することを確認した
- テスト条件を記録し、途中で中断した時点でも多数の失敗が出ていることを確認した
- スロットを固定し、2枚のDIMMを1枚ずつ同じ条件で比較した
- エラーが特定のDIMMに追従することを確認した

### 結論

問題はマザーボードのスロットではなく、特定のメモリモジュール側にある可能性が高いと判断できました。対象モジュールを保証対応・交換へ進め、切り分け中は容量を減らして運用しました。

### 学んだこと

- 一度再現しなかっただけでは「直った」と判断しない
- BIOS、スロット、モジュールなど複数の要因を、一度に変えずに比較する
- 同じスロット・同じ条件で1枚ずつ試験すると、エラーが部品へ追従するかを確認できる
- 初期仮説を修正できるよう、失敗した試験結果も含めて記録する

## 事例2：10GbEではなく2.5GbEへ通信が流れていた原因

### 状況

Windows PCには10GbE NICと2.5GbE NICがあり、10GbE側を主通信に設定していました。IPv4の経路と優先度を確認すると10GbE側が選ばれており、経路検索でも問題は見えませんでした。

それでも、ゲームのダウンロード中はタスクマネージャー上で2.5GbE側に大きな通信が表示されていました。

### 行った切り分け

推測で設定を変更せず、プロトコルごとに状態を分けました。

| 確認項目 | IPv4 | IPv6 |
|---|---|---|
| アドレス | 両方のNICで取得 | 2.5GbE側だけ取得 |
| デフォルトルート | 10GbE側を優先 | 2.5GbE側だけ存在 |
| 経路選択 | 10GbE側 | 2.5GbE側 |
| NIC側の有効状態 | 有効 | 10GbE側だけ無効 |

10GbE側のIPv6バインドが無効になっており、IPv6アドレスもデフォルトゲートウェイも取得していませんでした。そのため、接続先がIPv6を選ぶと、10GbE側ではなく2.5GbE側の経路しか使えませんでした。

### 修正と確認

10GbE側でIPv6を有効化し、次を確認しました。

- IPv6アドレスを取得すること
- IPv6デフォルトゲートウェイを取得すること
- IPv6デフォルトルートが10GbE側に作られること
- 経路検索で10GbE側が選ばれること
- 実際のダウンロード通信が高速側NICへ流れること

### 学んだこと

- NICのリンク速度とIPv4の優先度だけでは、実際に使われる経路を判断できない
- デュアルNIC環境では、IPv4とIPv6でアドレス、バインド、デフォルトルートを別々に確認する必要がある
- 設定画面の想定と、タスクマネージャーで見た実トラフィックが食い違う場合は、プロトコルごとの経路差を疑う
- 修正後は設定値だけでなく、実際の通信が目的のNICへ移ったことまで確認する
